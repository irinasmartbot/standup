## Итог

Проект содержит работающий MVP Telegram-бота, PostgreSQL-контура и desktop-админки, но не готов к безопасному масштабированию без стабилизационного цикла.

До расширения трафика нужно закрыть критичные риски:

- действия с чужой бронью через callback;
- гонку мест при подтверждении;
- неоднозначную идентичность событий без `event_id`;
- небезопасный выпуск через push в `dev`;
- fail-open настройки розыгрыша и админки;
- расхождение документации с кодом.

## Ключевые оценки аудита

- Документация: низкая зрелость. Документы есть, но часть устарела или противоречит коду.
- Код и архитектура: средняя зрелость. Есть модульная структура, но крупные файлы, sync-БД в async и legacy-код мешают сопровождению.
- Функциональная надежность: низкая. Основные ветки работают, но есть IDOR, гонка мест и неоднозначная идентичность события.
- База пользователей: низкая. Основа нормализована, но нет полной identity/retention/audit модели.
- Безопасность: низкая. Секретов в истории не найдено, но callback authorization и fail-open настройки критичны.
- Админка: desktop пригоден, mobile требует доработки.
- Тесты, CI, релиз: критично низкая зрелость. Есть мало тестов, нет полноценного CI, push в `dev` сразу разворачивается.

## P0 до расширения трафика

1. Авторизация брони.
   Каждый mutation/get-ticket SQL должен получать текущий `telegram_id` и возвращать 0 строк для чужого `booking_id`. Нужны негативные тесты.

2. Атомарные места.
   Подтверждение брони должно выполняться одной транзакцией с блокировкой или условием по `event_id`. Параллельный тест не должен превышать `max_seats`.

3. Стабильный `event_id`.
   Callback и booking state должны передавать `event_id`; одинаковые дата/время на разных площадках не должны смешиваться.

4. Идемпотентный билет.
   Сбой отправки не должен терять право пользователя на билет. Повтор должен возвращать существующий билет или безопасно завершать pending-состояние.

5. Безопасные настройки.
   `ROZYGRYSH_SKIP_SUB_CHECK` должен быть fail-closed по умолчанию, reset розыгрыша должен быть доступен только allowlist, admin не должен стартовать без auth.

6. CI и источник истины.
   Нужно выбрать основную ветку, сделать PR обязательным и запускать deploy только после зеленых checks из merge commit.

7. Правдивый README.
   В README должны быть актуальный entrypoint, точная версия Python, local/check/deploy и статус веток.

## Как применять

Аудит не означает, что все пункты нужно править в одном PR.

Безопасный порядок:

1. Docs-only фиксация аудита и плана стабилизации.
2. Отдельный stabilization PR без новых продуктовых функций.
3. Внутри stabilization PR: owner checks -> `event_id` -> atomic capacity/ticket -> tests/CI -> fail-closed config -> README/current state.
4. Users/admin/migrations вынести в следующий отдельный PR.
5. Production-деплой делать только после явного решения, проверок и rollback-плана.
