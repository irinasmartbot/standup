# Связь стендап-бота с Telegram

Обновлено: 26 ноября 2026 года.

## Что работает сейчас

Бот работает на сервере AdminVPS в России и соединяется с Telegram напрямую через **149.154.167.220:443**.

Переключение выполнено 26 ноября в 15:20 МСК. Telegram API ответил, бот возобновил получение событий, очередь сократилась с 25 до 0. Владелец проверил бота и подтвердил, что он отвечает.

**Автоматическое переключение и личные алерты ещё не включены.** Они находятся в настройке. Не считать описанную ниже целевую схему уже действующей.

## Что такое 149.154.167.220

Это IP-адрес на стороне Telegram, через который доступен Telegram Bot API — сервис для общения ботов с Telegram.

Обычно приложение обращается по имени `api.telegram.org`, а DNS выбирает IP-адрес. Во время сбоя DNS на сервере стендапа выдавал `149.154.166.110`; подключение к нему не проходило. Альтернативный адрес `149.154.167.220` прошёл проверку с того же сервера.

Бот и база остаются на AdminVPS. Для прямого пути не используется наш зарубежный сервер. Физическое расположение сервера Telegram по этому IP не проверялось.

Приложение сохраняет имя `api.telegram.org`, HTTPS, SNI и проверку сертификата Telegram. Меняется только адрес, к которому устанавливается сетевое соединение. Нельзя заменять URL на голый IP или отключать проверку сертификата.

## Два способа соединения

**Прямой путь, работает сейчас:**

```text
Бот на AdminVPS в РФ → 149.154.167.220 → Telegram
```

**Резервный путь через туннель:**

```text
Бот на AdminVPS в РФ → локальный порт 127.0.0.1:18443
                    → SSH-туннель → зарубежный VPS → Telegram
```

Туннель пересылает только соединения с Telegram API. Он не переносит бота, базу и файлы на зарубежный VPS.

Последняя отдельная проверка резервного пути 26 ноября перед переключением завершилась `ConnectionRefusedError`: локальный порт туннеля не принимал соединения. При этом systemd показывал сервис как `active`. Поэтому надпись `active` сама по себе не подтверждает работоспособность резерва.

## Как гости общаются с ботом

Гость пишет боту в Telegram. Бот на AdminVPS сам забирает новые события из Telegram с помощью long polling и отправляет ответы через Bot API. Для этого нужен рабочий исходящий путь с AdminVPS к Telegram.

Смена прямого пути на туннель не требует от гостя переходить в другого бота или менять настройки Telegram.

## Как будет работать автоматическое переключение

Статус: в настройке, ещё не включено.

1. Основной путь — прямое соединение с проверенным IP Telegram.
2. При сетевом сбое приложение пробует резервный SSH-туннель.
3. Пока основной путь недоступен, приложение использует рабочий резерв.
4. Прямой путь периодически проверяется. После восстановления приложение возвращается на него.
5. Если оба пути недоступны, бот временно не может получать сообщения и отправлять ответы. Работа возобновляется после восстановления хотя бы одного пути.

Защита от дублей обязательна: если ответ на `sendMessage` или `sendPhoto` потерялся, сообщение уже могло попасть в Telegram. Такой запрос нельзя безусловно повторять через другой путь. Безопасность повторов должна быть проверена до включения нового режима.

## Как будут приходить алерты

Статус: в настройке, доставка ещё не проверена.

Получатель — личный Telegram владельца, выбранный им в задаче. Числовой идентификатор получателя хранится только в конфигурации сервера.

Уведомления должны сообщать:

- основной путь недоступен и используется резерв;
- прямой путь восстановился;
- резервный туннель недоступен, хотя прямое соединение работает;
- оба пути недоступны;
- связь восстановлена.

Повторные одинаковые проверки не должны создавать поток одинаковых уведомлений. Неотправленные алерты должны сохраняться на сервере и переживать перезапуск мониторинга.

**Если оба пути к Telegram оборваны, мгновенно прислать алерт через Telegram невозможно.** Событие сохраняется и доставляется после восстановления связи с отметкой времени. Отдельный канал вне Telegram этой схемой пока не настроен.

## Текущая конфигурация после восстановления

Файл на VPS: `/home/standup/app/.env`.

```dotenv
TELEGRAM_RELAY_HOST=149.154.167.220
TELEGRAM_RELAY_PORT=443
TELEGRAM_RELAY_MODE=always
```

Название переменных историческое: сейчас этот механизм направляет защищённое соединение прямо на IP Telegram. Несмотря на слово `RELAY`, при этих значениях зарубежный туннель не используется.

Настройки применены перезапуском `standup-bot` и `standup-admin`. Код приложения остался на коммите `f8cecfdb694b00324721bdeb8f7ea909a34cde42`.

## Проверка с сервера стендапа

Прямой IP с сохранением имени и проверки сертификата:

```bash
curl --resolve api.telegram.org:443:149.154.167.220 \
  --connect-timeout 5 --max-time 10 -I https://api.telegram.org/
```

Туннель:

```bash
curl --connect-to api.telegram.org:443:127.0.0.1:18443 \
  --connect-timeout 5 --max-time 10 -I https://api.telegram.org/
```

HTTP-ответ подтверждает доступность соединения. Для проверки приложения дополнительно нужны `getMe`, `getWebhookInfo`, журнал получения событий и реальный ответ бота. Не выводить токены и полные URL с токенами в журнал.

## Откат переключения от 26 ноября

Резервная копия `.env` и скрипт отката сохранены на VPS:

```text
/home/standup/backups/telegram-ip-20261126T122036Z/env.before
/home/standup/backups/telegram-ip-20261126T122036Z/rollback.py
```

Команда на VPS от пользователя проекта:

```bash
/home/standup/app/venv/bin/python \
  /home/standup/backups/telegram-ip-20261126T122036Z/rollback.py
```

Скрипт восстанавливает прежний `.env` и перезапускает бота и админку. Он проверяет, что после переключения `.env` не менялся; при более новых изменениях откажется затирать их.

Откат возвращает прежний путь через локальный туннель. Если туннель всё ещё не работает, после отката бот снова потеряет связь. Сначала проверить резервный путь.
