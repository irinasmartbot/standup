## 2026-07-24 — Перенести регламент в будущую ветку main

Статус: accepted
Владелец решения: Ирина
Связано с: `AGENTS.md`, `docs/agent-regulation.md`, ветка `docs/agent-regulation`

Описание:
Не мержить регламент в текущую ветку `dev`, потому что push/merge в `dev` запускает deploy на VPS. Когда рабочей веткой проекта станет `main`, перенести туда коммит с регламентом.

Зачем:
Нужно применить регламент к основной рабочей ветке проекта без лишнего production-деплоя из `dev`.

Границы:
- Входит: merge ветки `docs/agent-regulation` в `main` или cherry-pick коммита `c3096da`.
- Не входит: merge в `dev`, push в deploy-ветку, изменение workflow деплоя.

Риски и вопросы:
- Перед переносом нужно проверить, какая ветка запускает production-деплой на тот момент.
- Если workflow будет перенесен с `dev` на `main`, merge в `main` тоже может запускать deploy и потребует отдельного разрешения.

## 2026-07-24 — Стабилизационный PR по P0-находкам аудита

Статус: proposed
Владелец решения: не назначен
Связано с: `docs/technical-audit-2026-07-24.md`

Описание:
Подготовить отдельный stabilization PR без новых продуктовых функций, чтобы закрыть P0-находки технического аудита.

Зачем:
Аудит выявил критичные риски перед расширением трафика: действия с чужой бронью, гонка мест, отсутствие стабильного `event_id`, fail-open настройки и небезопасный выпуск через push в `dev`.

Границы:
- Входит: server-side owner checks для booking callbacks, переход callback/state на `event_id`, атомарная проверка вместимости, идемпотентная выдача билета, fail-closed настройки, минимальный CI/check и актуализация README/current-state.
- Не входит: новые продуктовые функции, полноценная CRM, большая переработка админки, production-деплой без отдельного разрешения.

Риски и вопросы:
- Нужно выбрать целевую рабочую ветку перед началом: текущий `dev` или будущий `main`.
- Нужны негативные тесты IDOR и конкурентный тест вместимости.
- Нужно отдельно решить, когда и как менять deploy workflow, чтобы не сломать текущий выпуск.

## 2026-09-14 — Кнопка рассылки запускает бронь сольника 15.09

Статус: done
Владелец решения: Ирина
Связано с: вкладка «Рассылка», `booking_resident`, проверка материала

Описание:
Галочка в форме рассылки: кнопка без URL запускает тот же сценарий брони, что карточка проверки на 15.09 20:00 Temple Bar.

Зачем:
Анонс сольника уходит по базе TG+VK, а «Забронировать» не должен открывать ссылку или слать доп. текст.

Границы:
- Входит: служебный follow-up `__flow:booking_resident__`, обработчики `mail_fu` в Telegram и VK.
- Не входит: произвольное мероприятие из формы, кнопка рассылки на другие форматы.

Риски и вопросы:
- Нужны рестарт админки, Telegram-бота и VK-бота, иначе клик не начнёт бронь.

## 2026-09-17 — Сольник 15.09: входы закрыты

Статус: done
Владелец решения: Ирина
Связано с: `booking_resident`, VK Mini App, рассылка

Описание:
Шоу 15.09 прошло. Живой старт брони сольника убран. Старые ссылки и кнопки отвечают текстом «предложение уже неактуально» / «шоу уже прошло», без 404 и без сценария брони.

Границы:

- Не входит: общая бронь проверки материала, HTML-карточки/постеры как заготовка.

## 2026-09-17 — Рассылка: каты, шаблоны, планирование

Статус: done
Владелец решения: Ирина
Связано с: вкладка «Рассылка»

Описание:
Фильтры аудитории и блок «отмена шоу + даты розыгрыша» спрятаны под кат. Можно выбрать и сохранить 4 шаблона текста (BEST TG/VK, музлото TG/VK). Рассылку можно запланировать, перенести, отправить сразу или отменить.

Зачем:
Редкие фильтры занимали экран; один и тот же анонс вставляли каждый раз; нельзя было отложить отправку.

Границы:
- Входит: UI катов, `mailing_templates`, `scheduled_at`, кнопки Перенести / Сейчас / Стоп.
- Не входит: отдельный календарь кампаний, повтор по cron, разные тексты TG+VK в одной кампании «Оба».

Риски и вопросы:
- Аудитория считается в момент создания кампании, не в момент отправки.
- Нужен рестарт админки и `standup-bot` (воркер рассылки).
