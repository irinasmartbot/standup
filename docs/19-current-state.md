# Текущее состояние проекта

Дата обновления: 2026-07-24

Этот файл описывает фактическое состояние реализации по данным репозитория. Он не является доказательством production сам по себе: для production-вопросов нужны health-check, логи, база данных или целевая проверка сценария.

## Реализовано

- Telegram-бот для бронирования мест на мероприятия Moscow StandUp Show.
- Главное меню с разделами бронирования, форматов, площадок, правил, менеджера и канала.
- Формат `StandUp Проверка материала`.
- Загрузка афиши из опубликованной Google-таблицы CSV.
- Выбор мероприятия по дате или площадке.
- Бронирование с именем, телефоном и количеством гостей.
- Ограничение до 4 гостей на одну бронь.
- Проверка лимита мест по мероприятию.
- Отмена брони, смена даты и изменение количества гостей.
- Генерация билета через Pillow.
- Напоминания и аннулирование неподтвержденных броней.
- Визуальная админка бронирований.
- Owner-режим админки для просмотра базы при наличии `ADMIN_OWNER_TOKEN`.
- PostgreSQL-схема для серверного контура.
- Скрипты импорта и синхронизации событий из Google Sheets.
- VK-направление и розыгрыш находятся в коде и документах, но их production-статус требует отдельной проверки.

## Не завершено или требует уточнения

- Технический аудит от 2026-07-24 выявил P0-риски, которые нужно закрыть до расширения трафика: IDOR в callback брони, гонка мест, отсутствие стабильного `event_id`, fail-open настройки, прямой deploy из `dev` без CI и устаревшие документы.
- Полная ветка `StandUp BEST`.
- Ветка формата `1+1`.
- Ветка мастер-классов с оплатой и проверкой чека.
- Ветка розыгрыша из Telegram-канала.
- Полнота админ-панели и выгрузки для менеджера требует уточнения относительно текущего кода и production.
- Rollback-процедура не зафиксирована в репозитории.
- Staging/test окружение не зафиксировано в репозитории.
- Владельцы продуктовых и технических решений не зафиксированы в репозитории.
- Мониторинг и порядок просмотра логов описаны частично через deploy workflow и VPS/systemd, но отдельный операционный документ отсутствует.

## Production-контур

Из репозитория видно:

- push в `dev` запускает `.github/workflows/deploy-dev.yml`;
- workflow подключается к VPS по SSH;
- код на VPS приводится к `origin/dev`;
- устанавливаются зависимости из `requirements.txt`;
- выполняются подготовка таблиц и импорт событий из Google Sheets;
- перезапускается `standup-bot`;
- health-check проверяет активность systemd-сервиса.

Фактическое состояние production нужно проверять отдельно на сервере: active service, логи, миграции, данные и пользовательские сценарии.
